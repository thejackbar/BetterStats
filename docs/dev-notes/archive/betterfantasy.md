## v9.106.6 (2026-10-05): unsettle, live points on a long round, Better HQ competitions list

Reported: a round settled by accident could not be undone; a two-week round showed no points until it ended; Better HQ could not see every club's competition.

- `fantasy_engine.unsettle_round` and `POST /club-admin/fantasy/rounds/{id}/unsettle`. - `public_fantasy.live` used `squad.total_points + round points`; with provisional rows stored that counted the round twice. It now subtracts the stored round row first.
- `GET /club-admin/fantasy/super/competitions` (super admin) and `SuperFantasyCompetitions.jsx`. `switchClub` takes an optional landing path.
- Caught while verifying: `routers/fantasy.py` had no `text` import, which would have 500ed the new endpoint.

## v9.110.6 (2026-10-12): player prices move on performances

The design (docs/betterfantasycricket.md) said prices rise and fall through the season, but nothing wrote them: `fantasy_pool_players.current_price` was set only at pool build, by an admin edit or when a player was added, `price_change` was read by the API and never written, so every arrow and the "price moves" notification were empty and the sell-on rule (buy price plus half the rise) had no rise to pay.

`services/fantasy_pricing.py` replays the season's scored rounds onto each player's `base_price` (see the guide for the rule: form over the last 3 played rounds blended with 2 rounds at the starting price's implied points, a half-way step, 0.1 rounding, capped at 0.5 a round, floor 4.0, no move when the player did not play, manual round scores count as played). Replay, not increment, because settlement is meant to be repeatable: a late scorecard re-settles a scored round, an admin can unsettle one, and an increment would double count. `settle_round` (both exits), `unsettle_round` and `build_pool(reset=True)` call it; the nightly job calls it for every season, which is also the catch-up for rounds scored before this release. `python -m app.scripts.fantasy_recompute_prices <org|all> [--apply]` shows or does the catch-up now. Ownership change, in the original design, was left out: there is no per-round ownership history to replay from.

Hand-set prices: `fantasy_pool_players.price_locked` (migration 326, `services/fantasy_price_ddl.py`). The DDL is a `DO` block that adds the column and, only on the run that creates it, locks every player whose `current_price` differs from `base_price`, since until now only an admin edit or a mid-season rebuild could cause that and managers bought at those prices. Later boots do nothing. The admin PATCH locks on a typed price; `price_locked: false` hands it back and replays. `build_pool` with `reset` clears locks; without `reset` it now keeps `base_price` as well as `current_price` for existing players, otherwise a pricing-window change would shift live prices through the replay.

Budget: `_sell_value` now returns the current price (was purchase + half the profit, floored at the purchase price, so a fall cost nothing). `/me` squad players carry `price`, `price_change` and `sell_value`; the pool and admin pool carry `price_change`. The notification id for a price move includes the amount so a second move is not hidden by an earlier read. Front end: `PriceArrow` and `PriceTag` in `pages/fantasy/ui.jsx` on My Team, Pick Squad, Transfers (mobile and desktop), the Players list, profile and compare header, and the admin pool table. Pick Squad's rebuild starts from the squad's current prices, which is what the server charges.

`verify_fantasy_pricing.py` (38 checks): the rule's cap, floor and no-play; a settle moves A up and B down by the cap; a second settle moves nothing; unsettle returns to base; a hand-set price survives and can be handed back; a season scored before the release catches up to the same prices, dry run writes nothing; a sale banks 92.5 and 84.5 where the old rule gave 92.2 and 85.0; the DDL locks once; a reset rebuild replays the rounds onto the new baseline and clears locks. The control (previous commit) fails on exactly the movement, the sale figures and the missing payload keys. The UI was driven in Chromium at 390px and 1280px with the API stubbed (arrow colours, no overflow, the transfer request on the wire).

## v9.110.7 (2026-10-12): the round lock, an editable lock time, and transfers queued behind it

A round already locked its XI, captain and chips at `lock_at`, but a transfer in that window was refused with a 403 until the round was scored (up to a fortnight for a long round), and the design said "transfers confirmed after the lock apply to the next round". Two other problems found on the way: `generate_rounds` set `lock_at` to midnight of the first game day with no time zone, which Postgres reads as UTC, so rounds locked at 11am Melbourne (10am in winter) and a 9am game could still be edited after it started; and the nightly `generate_rounds` overwrote `lock_at`, so nothing an admin set would have lasted.

Lock: one deadline per round (option A, FPL style). `fantasy_engine.default_lock_at` gives 09:00 in `lock_timezone` (default Australia/Melbourne) on the first game day; both are optional season rules. `fantasy_rounds.lock_manual` (migration 327, `services/fantasy_queue_ddl.py`) marks a time an admin set; the upsert in `generate_rounds` keeps it, and the surplus-round delete now also checks `fantasy_queued_transfers`. `PATCH /club-admin/fantasy/rounds/{id}/lock` sets it (ISO date-time with offset) or, with `null`, goes back to the default; a scored round is refused with 409. The Overview rounds table has a Locks column with Change, Save and Use the default. The synced draw does carry `startDateTime` per match, but the stored games only hold dates and I could not confirm the feed's offset convention, so the default does not use it; an admin's time is exact.

Queue: `fantasy_queued_transfers` (squad, the round it waits on, out and in player, status pending/applied/cancelled, reason, and what the carry-out used so it can be reversed). `public_fantasy.transfer` queues when `_round_locked` instead of 403 (captain, vice, chip and rebuild routes still refuse). The squad's picks are untouched while a transfer waits, so the locked round is scored with the XI that was locked without a lock-time snapshot. `settle_round` calls `fantasy_queue.apply_pending` after `recompute_prices`, so prices are the ones AFTER the round. At carry-out: out player still in the team, in player not, available and the same role, bank not below zero after the swap (else cancelled with a reason), a free transfer if the squad has one (settlement has just banked the round's) else the hit, tallied on the next round via `fantasy_squad.record_round_transfer`, purchase price the post-settle price, ownership recounted, transactions written. The armband passes with the player (a captain can be queued out because the captain cannot be changed while locked). At queue time an unaffordable swap is a warning, not a refusal, because prices move. `unsettle_round` calls `revert_applied` first: it puts back each carried-out transfer when the player who came in is still there and the one who went out is not (bank, free transfer, tally restored, row back to pending) and leaves any other as it happened. Re-settling a scored round finds nothing pending. `record_round_transfer` and `recount_ownership` moved into `fantasy_squad` (the router's helpers delegate).

Screens: Transfers works while locked (amber explanation, "Queue transfer", a Queued transfers list with Cancel, queued players marked, cancelled ones shown with the reason; its list hook now sits above the early return). My Team says the XI is frozen and how many transfers are queued. `/me` carries `queued_transfers` and `round.next_number`; the notification feed carries queued and cancelled items. `fantasy_queued_transfers` is on `merge_carry.CARRIED` (both player columns, club guard through the squad); the player-merge verifier seeds it.

`verify_fantasy_lock_queue.py` (41 checks): captain and chip refused after the lock; a transfer queues and touches nothing; validation; the warning; cancel keeps the row; the locked round is scored with the locked XI; carry-out at post-settle prices with the free/hit split and the next-round tally; armband; a cancel with a reason when the bank falls short; a second settle changes nothing; unsettle puts it all back and settling again repeats it exactly; an unsafe reversal is left alone. `verify_fantasy_rounds.py` section 2b (6 checks) covers the default, the admin time, surviving the refresh, null and the scored-round refusal. The control (previous commit) fails on exactly the 403 for every transfer after the lock and the absent queue. UI driven in Chromium at 390px and 1280px with the API stubbed (the queue request on the wire, the queued list, cancel, the admin save sending 23:30Z for 10:30 Melbourne, no overflow).

## v9.110.8 (2026-10-12): prices that move gently, and price movers

Reported once prices were live: nearly everyone had gone up the 0.5 cap, and at Scarborough a player on 41 points rose as far as one on double that. Cause, reproduced on the shipped rule: `step_price` measured a score against the points the player's STARTING price implies (`(base - 4.0) / 0.12`). A player on or near the floor price implies about 0 to 8 points, while a real round scores tens, so the gap was always large and the half-gap step hit the cap: `step_price(4.0, 4.0, [41])`, `[82]` and `[150]` all gave +0.5, and even 10 points gave +0.2. The starting prices are built from season aggregates that stand in for per-innings milestones, so they run low for exactly the players who are priced low, and nothing in the rule corrected for it.

Fix: the rule is now relative to the round itself (`fantasy_pricing.peer_moves`, `replay_season`). For each round the players who played give (points per game, price at the start of the round); a straight line through them (slope steadied towards the starting-price scale, `SLOPE_SHRINK` 15) says what a price is worth in that round; a player's surprise is points less that line, which nets to nothing across the round, so the pool cannot all drift one way and a flat track or a low-scoring grade moves nobody. Move = surprise / `MOVE_SCALE` (200), rounded to 0.1 and capped at 0.5, so a century is the 0.5, an 80 from a cheap player about 0.2, an ordinary good day 0.1 and double the score about double the move. Round-major replay (the line needs everyone's price at the same time), a locked price is a data point that never moves, fewer than `MIN_PEERS` (6) players moves nobody, points are per game so a two-game round is not double. `recompute_prices` still replays from `base_price`, so the nightly run rewrites every price the first rule produced; no data fix is needed. Sales made at the first rule's prices are not reversed.

Movers: `price_change` (latest scored round) now drives All / ▲ Risers / ▼ Fallers chips and Biggest rise / Biggest fall sorts on the member Players list, Pick Squad and Transfers (desktop and phone). ## Fielding from every innings counts (v9.123.2.2, Oct 2026)
